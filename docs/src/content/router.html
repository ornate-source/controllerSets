Options available in createRouter (no file upload)

Equality works on fields in query; range and compare on fields in filterableFields. Range bounds and numeric-looking compare values are treated as numbers. One range and one compare filter per request — use QUERY for more.

Searching

GET /api/products?s=oak
GET /api/products?search=oak          # same thing
  • Case-insensitive, matches anywhere in the text: oak finds "Oak chair" and "Cloak".
  • Searches every field in the server's search list — a match in any one counts.
  • Matched literally: .* or ( are just characters.
  • Combines with filters: ?s=oak&category=chairs = oak items that are chairs.
  • Up to 128 characters.

Sorting

GET /api/products?sort=price          # cheapest first
GET /api/products?sort=-price         # most expensive first
  • One field per request, from the server's sortableFields. - means descending.
  • Without sort, the server's default order (orderBy) applies.
  • Need several sort keys? Use QUERY: "sort": ["-price", "name"].

Pagination

Page numbers (the default). Add page to paginate; pageSize sets the size.

GET /api/products?page=2&pageSize=20
{
  "success": true,
  "data": [ … 20 records … ],
  "pagination": { "currentPage": 2, "pageSize": 20, "totalPages": 7, "totalRecords": 132 }
}
  • Without page, the list is not paginated but still capped (100 records by default).
  • pageSize defaults to 50 and is capped by the server's maxLimit.
  • Some servers skip counting: then pagination has hasMore instead of totalPages.

Cursor (when the server sets pagination: 'cursor'). No page numbers — follow nextCursor:

GET /api/events?pageSize=50
→ { "data": [ … ], "pagination": { "pageSize": 50, "hasMore": true, "nextCursor": "eyJpIjoi…" } }

GET /api/events?pageSize=50&cursor=eyJpIjoi…
→ … until "hasMore": false

QUERY: filters in a JSON body

For filters too long or complex for a URL. Same response as GET. Requires the server on Node 22.2+.

const res = await fetch('/api/products', {
  method: 'QUERY',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    filter: {
      category: ['chairs', 'tables'],          // any of
      price: { gte: 50, lte: 200 },            // range
      inStock: true,                           // equals
    },
    search: 'oak',
    sort: ['-price', 'name'],              // several keys
    page: 1,
    pageSize: 20,
  }),
});
Body keyMeaning
filterField → value, array (any of), or operators: eq ne gt gte lt lte in nin — no $.
searchSearch term.
sortA field, or up to five: ["-price", "name"].
page, pageSizePage numbers.
limitCap an unpaginated list (not with page).
cursorNext page in cursor mode.

Two routers, one model

The most common shape: the public reads, staff edit. Each router carries its own allowlists, so the public one can never write — even if a guard is misconfigured.

const catalogue = {
  model: Product,
  orderBy: '-createdAt',
  query: ['category', 'isFeatured'],
  search: ['name', 'description'],
  filterableFields: ['price', 'category'],
  sortableFields: ['price', 'name', 'createdAt'],
};

// Anyone: read
app.use('/api/products', createRouter({ ...catalogue, allowedFields: [] }));

// Staff: read and write
app.use('/api/admin/products', createRouter({
  ...catalogue,
  middlewares: [auth.requireAuth, auth.requireRole('staff', 'admin')],
  allowedFields: ['name', 'price', 'description', 'category', 'isFeatured'],
}));
Server-owned fields

Fields like author, ownerId or tenantId come from the signed-in user, never from the body. Keep them out of allowedFields and set them in validate.create — whatever the client sent for them was already stripped.

app.use('/api/posts', createRouter({
  model: Post,
  middlewares: [auth.requireAuth],
  allowedFields: ['title', 'body', 'tags'],          // no 'author'
  validate: {
    create: (payload, { req }) => ({ ...payload, author: req.auth.userId }),
  },
}));
Only my records

Three pieces: force the owner into every list, check ownership on every /:id, and stamp the owner on create. Tested end to end — a user cannot list, read, change or delete another user's records, even by sending ?ownerId= themselves.

import express from 'express';
import mongoose from 'mongoose';
import { createRouter, HttpError } from 'express-controller-sets';

// 1. Lists: pin ownerId to the caller. Express 5 re-parses req.query on every
//    read, so assigning to it does nothing — shadow it with a real property.
const onlyMine = (req, res, next) => {
  Object.defineProperty(req, 'query', {
    value: { ...req.query, ownerId: String(req.auth.userId) },
    writable: true, configurable: true, enumerable: true,
  });
  next();
};

// 2. Single records: 404 unless the caller owns it (404, not 403 — don't
//    confirm that someone else's record exists).
const ownsNote = async (req, res, next) => {
  if (!mongoose.isValidObjectId(req.params.id)) return next();   // the controller answers 400
  const mine = await Note.exists({ _id: req.params.id, ownerId: req.auth.userId });
  if (!mine) throw new HttpError(404, 'Entry not found.');
  next();
};

const notes = express.Router();
notes.use(auth.requireAuth, onlyMine);
notes.use('/:id', ownsNote);
notes.use(createRouter({
  model: Note,
  orderBy: '-createdAt',
  query: ['ownerId'],
  enableQuery: false,                                  // QUERY filters from the body — keep it off here
  allowedFields: ['title', 'body'],
  validate: { create: (p, { req }) => ({ ...p, ownerId: req.auth.userId }) },   // 3. stamp the owner
}));

app.use('/api/notes', notes);

Don't skip step 2. The list filter only covers GET /. Without the /:id check, anyone who learns an id can read, edit or delete that record.

Populate & search a ref

onGet decides, per request, what to populate and select. Search can reach into a referenced model with a dotted path.

app.use('/api/books', createRouter({

    populates: [{ path: 'author', select: 'name avatar' }],

Validate & normalise

Throw ValidationError with a field map and the client gets it back as fields. Return an object to replace the payload — that is how you trim, lowercase or derive values.

import { createRouter, ValidationError } from 'express-controller-sets';

const check = (p) => {
  const fields = {};
  if (p.price !== undefined && !(p.price >= 0)) fields.price = 'must be zero or more';
  if (p.sku !== undefined && !/^[A-Z0-9-]{4,20}$/.test(p.sku)) fields.sku = 'use 4–20 letters, digits or dashes';
  if (Object.keys(fields).length) throw new ValidationError('Check the submitted values.', fields);
  return p.name ? { ...p, name: p.name.trim() } : p;
};

createRouter({
  model: Product,
  allowedFields: { create: ['name', 'price', 'sku'], update: ['name', 'price'] },   // sku is set once
  validate: { create: check, update: check },
});
{ "success": false, "error": "Check the submitted values.",
  "fields": { "price": "must be zero or more" } }
Large collections

Offset pages get slower the deeper you go, and counting every match costs a full scan. Cursor pagination is one index seek per page at any depth. Index the sort field.

// Schema: eventSchema.index({ createdAt: -1 });

app.use('/api/events', createRouter({
  model: Event,
  orderBy: '-createdAt',
  pagination: 'cursor',       // follow pagination.nextCursor: ?cursor=…
  maxTimeMS: 2000,            // a slow query is cut off, not left running
  allowedFields: [],
}));

If you need page numbers but not totals, keep offset pagination and set countStrategy: 'none' — responses carry hasMore instead of totalPages.

Guards, tenancy and per-user data

The library builds the routes. Deciding who may call them is entirely yours.

createRouter({
  model: Order,
  middlewares: [requireAuth, requireRole('staff')],   // run before every route
  allowedFields: ['status', 'note'],
});

Everything in middlewares is applied with router.use(), so it guards all five endpoints in that router. When different verbs need different rules, use two routers on the same path:

// Public: anyone may read the catalogue
app.use('/api/products', createRouter({
  model: Product,
  query: ['category'],
  allowedFields: [],                       // no writes get through here
}));

// Private: only staff may change it
app.use('/api/admin/products', createRouter({
  model: Product,
  middlewares: [requireAuth, requireRole('staff')],
  query: ['category'],
  allowedFields: ['name', 'price', 'category', 'isFeatured'],
}));

Per-user data ("show me only my orders") needs your own middleware. The library has no concept of ownership. Constrain the query yourself before it reaches the controller, and remember that a client can still ask for any ID on /:id unless you check there too.

// A tenancy guard: force every list request to be scoped to the caller.
//
// Express 5 re-parses req.query on every read, so `req.query.owner = …` is
// silently thrown away and the client's own ?owner= wins. Shadow the getter
// with a real property instead.
const onlyMine = (req, res, next) => {
  Object.defineProperty(req, 'query', {
    value: { ...req.query, owner: String(req.auth.userId) },  // 'owner' must be in `query`
    writable: true, configurable: true, enumerable: true,
  });
  next();
};

createRouter({
  model: Order,
  middlewares: [auth.requireAuth, onlyMine],
  query: ['owner', 'status'],
  enableQuery: false,   // QUERY reads its filter from the body, not req.query
});

That guard covers GET / only — which is why the example turns off QUERY /, whose filter arrives in the body. GET /:id, PATCH /:id and DELETE /:id address a record directly, so add a middleware that loads the record and compares its owner — or keep those verbs on an admin-only router.

Everything about validate

Two gates stand between a request body and your collection, and they answer different questions.

The field policy

allowedFields decides what a client may set. A question of authority — not yours to delegate.

Your validator

validate decides whether the values make sense. A question only your domain can answer.

The schema

Mongoose's own validators run last, unchanged — types, required, enum, your custom paths.

The order matters: your hook is handed the payload after the field policy has filtered it, so it never has to wonder whether role in front of it came from an admin or from a stranger. It cannot be there.

import { createRouter, ValidationError } from 'express-controller-sets';

createRouter({
  model: Product,
  allowedFields: ['name', 'price', 'sku'],

  validate: {
    create: async (payload, { req }) => {
      if (payload.price < 0) {
        throw new ValidationError('Check the submitted values.', {
          price: 'must not be negative',
        });
      }

      if (await Product.exists({ sku: payload.sku })) {
        throw new ValidationError('That SKU is taken.', { sku: 'already in use' });
      }

      // Returning an object replaces the payload: normalise what came in,
      // and set fields the client is not allowed to send.
      return { ...payload, name: payload.name.trim(), ownerId: req.user.id };
    },

    update: (payload) => {
      if (payload.price === 0) throw new ValidationError('Price cannot be zero.');
    },
  },
});

Pass a single function instead of { create, update } to run the same rules on both.

What the hook receives

Argument What it holds
payload The body, already filtered to the fields this client may write. Never empty — an empty one is a 400 before the hook runs.
context.req · context.res The Express request and response, for req.user, headers, uploaded files.
context.operation 'create' or 'update' — useful when one function serves both.
context.id The target document's id on an update; undefined on a create.
context.model The Mongoose model, so a uniqueness check needs no extra import.

What it may return, and what it may throw

The hook… Result
returns nothing The payload is written as filtered. The common case.
returns an object That object is written instead — your chance to normalise values or add server-owned fields.
throws ValidationError 400 (or the status you pass) with a fields map.
throws any HttpError That status, with your message. Use it for 403 and friends.
throws anything else 500, with the detail kept in your log and out of the response.
is async Awaited. Query the database in it if the rule needs to.

The rejection a client sees

// 400 Bad Request
{
  "success": false,
  "error": "Check the submitted values.",
  "fields": { "price": "must not be negative" }
}

fields appears only when there is one, so a client that never looks for it sees the shape it always has. Mongoose validation failures and duplicate-key conflicts fill it in too, which means one rendering path on the client covers every rejected write. It is never sent on a 5xx — an internal failure's detail is not the caller's business.

Your hook runs before the schema, so required fields may be missing. That ordering is deliberate — it is what lets a hook supply a required field like ownerId before Mongoose checks for it. The corollary is that payload.name.trim() throws when the client omitted name, and an unexpected throw is a 500. Check before you dereference:

validate: (payload) => ({
  ...payload,
  // not payload.name.trim() — `name` may not be here yet
  ...(payload.name ? { name: payload.name.trim() } : {}),
});

A validator is not a substitute for allowedFields. It runs on what the policy already let through, so a model with no policy hands your hook every schema field and trusts you to remember which ones a stranger may set. Configure both.

A returned object is trusted, but not blindly. Your hook runs on the server, so it may set fields no client can. Keys that are syntax rather than data — $-prefixed, dotted, or __proto__ — are still stripped from what it returns. No legitimate hook needs them as field names.

Everything about runAfterCreate

Run something once a record exists — send a welcome email, push a job onto a queue, warm a cache.

createRouter({
  model: User,
  allowedFields: ['name', 'email'],

  runAfterCreate: async (user) => {
    await sendWelcomeEmail(user.email);
    await queue.add('index-user', { id: user._id });
  },
});

The hook receives the created document and is awaited before the 201 goes out.

Default

Failures are logged, not raised

If the email service is down, the user is still created and the client still gets 201. The record exists, so reporting failure would tell the client to retry a write that already landed.

strictAfterCreate: true

Failures propagate

The error reaches your errorHandler and the client sees a 500 — even though the record was created. Choose this only when a missed side effect is worse than a confusing response.

Keep it short. The client is waiting on this hook. Anything slow or failure-prone belongs on a queue — enqueue inside the hook, do the work elsewhere.

How writes are filtered

The request body is filtered before Mongoose ever sees it. This section is the single most important one for security.

Say what a client may write

// Allowlist — name what IS writable (recommended)
createRouter({
  model: User,
  allowedFields: ['name', 'email', 'avatar'],
});

// Blocklist — name what is NOT writable
createRouter({
  model: User,
  blockedFields: ['role', 'isAdmin', 'balance'],
});

// Per verb — stricter on update than on create
createRouter({
  model: User,
  allowedFields: {
    create: ['name', 'email', 'password'],
    update: ['name', 'avatar'],          // email and password need their own flow
  },
});

Both options may be combined; blockedFields is applied after allowedFields, so a field on both lists is blocked.

Mongoose's strict mode is not a substitute for this. Strict mode drops keys your schema doesn't define — it throws away typos and faithfully saves {"role": "admin"}, because role is a real field. The only thing standing between a signup form and an admin account is a field policy.

What a client sends vs. what gets saved

// allowedFields: ['name', 'email']

// The client POSTs:
{
  "name":  "Ayesha",
  "email": "ayesha@example.com",
  "role":  "admin",          // ✘ not allowlisted        → dropped
  "_id":   "65af…",          // ✘ always immutable       → dropped
  "$where": "1 === 1"        // ✘ Mongo operator syntax  → dropped
}

// What reaches the database:
{ "name": "Ayesha", "email": "ayesha@example.com" }

Dropped fields are dropped quietly — the request still succeeds with the fields that survived. One exception: if nothing survives, you get 400 "Request body contains no writable fields." rather than an empty record being created.

Debugging a field that "won't save"? Nine times out of ten it isn't in allowedFields. Check that list first, then check for a typo against the schema.

Everything about onGet

One hook that decides, per request, which relations to expand and which fields to return.

Populating relations is expensive, and different callers need different amounts of data. A mobile list view wants names; an admin screen wants everything. onGet lets one router serve both.

onGet: (req, res) => ({
  populates: [],   // Mongoose .populate() argument — string, object, or array
  selects: '',     // Mongoose .select() argument — e.g. 'name price -_id'
})
createRouter({
  model: Product,
  onGet: () => ({
    populates: 'category',
    selects: 'name price category',
  }),
});

The hook receives the live req, so anything your auth middleware attached is available.

createRouter({
  model: Order,
  middlewares: [requireAuth],
  onGet: (req) => {
    if (req.user?.role === 'admin') {
      return {
        populates: [
          { path: 'customer', select: 'name email phone' },
          { path: 'items.product', select: 'name price' },
        ],
        selects: '',                       // everything
      };
    }
    return { populates: 'items.product', selects: '-internalNotes -margin' };
  },
});

Keep list responses light and expand only on the single-record route.

const onGet = async (req) => {
  const isDetail = Boolean(req.params.id);
  return {
    populates: isDetail ? ['category', 'reviews'] : 'category',
    selects: isDetail ? '' : 'name price category',
  };
};

createRouter({ model: Product, onGet });   // reuse across routers
Route onGet applies?
GET /✔
QUERY /✔
GET /:id✔
PATCH /:id (the returned document)✔
POST /✘ — returns the created document as-is
DELETE /:id✘ — returns a message, not a document

If your hook throws, the request still succeeds. The error is logged and the request falls back to no populate and no select. That keeps a broken hook from taking down every read — but it also means a hook you rely on to hide fields could silently stop hiding them. Use selects for convenience; use schema toJSON transforms or a separate router for anything that must never be returned.

A note on lean. Reads return real Mongoose documents by default, so schema.set('toJSON', { transform }) runs and any fields you strip there really are stripped. lean: true is faster but bypasses those transforms — only enable it if you have checked that nothing sensitive was relying on them.

Every query parameter

Everything GET / understands. For the body form of the same read, see HTTP QUERY.

Parameter Example Notes
page ?page=2 Switches on the pagination block. Starts at 1; junk values become 1.
pageSize ?pageSize=20 Default 50, clamped to maxLimit.

sort ?sort=-price Must be in sortableFields, else 400. - means descending.
any field named in query ?category=65af… Equality filter. Repeat the parameter for an $in match.

compareField + compareValue ?compareField=price&compareValue=50 Field must be in filterableFields. Numeric-looking values become numbers.

In cursor mode two more apply: ?cursor= continues a scan from a previous response's nextCursor, and ?page= is refused.

Putting several together

# featured laptops between 500 and 1500, cheapest first, second page of 20
GET /api/products
      ?isFeatured=true
      &s=laptop
      &rangeField=price&range=500-1500
      &sort=price
      &page=2&pageSize=20

Filters combine with AND. The search term is the one exception: it becomes an OR across your search fields, and that whole group is ANDed with everything else.

{

const res  = await fetch('/api/products?page=1');
const body = await res.json();

body.data;                    // always an array here

HTTP QUERY in depth

The same read as GET /, described by a JSON body instead of a URL — for filters that are too long, too structured, or too sensitive to put in a query string.

QUERY is a real HTTP method (RFC 10008), and like GET it is safe and idempotent: it never writes anything. The difference is only where the parameters live.

URLs run out

Proxies and servers cap request lines around 4–8 KB. Two hundred ids in an in list is not a URL.

URLs get logged

Query strings land in access logs, proxy logs, browser history and Referer headers. Bodies do not.

Structure survives

Two bounds on one field, a multi-key sort, a list of values — all say what they mean, without encoding tricks.

A request

QUERY /api/products HTTP/1.1
Content-Type: application/json

{
  "filter": {
    "category": "65af…",
    "price":    { "gte": 50, "lte": 250 },
    "tag":      ["sale", "clearance"]
  },
  "search": "office chair",
  "sort":   ["-price", "name"],
  "page":   1,
  "pageSize": 20
}

The response is exactly what the equivalent GET would have returned — same envelope, same pagination block, same onGet shaping, same maxLimit cap. Nothing about the read changes; only the request does.

The body is not a MongoDB query. Operators are written without $ and looked up in a fixed table, so a body carrying $where or $function fails that lookup instead of reaching the driver. Field names are checked against the same allowlists ?sort= and ?rangeField= use.

What the body may contain

Key Type Meaning
filter object Field → condition. Every field must be in filterableFields (which defaults to query).
search string Same term, same fields and same escaping as ?s=. Capped by maxSearchLength.
sort string · string[] "price" or "-price". A list sorts on several keys, up to five, each checked against sortableFields.
page integer ≥ 1 Switches on the paginated response. Cannot be combined with limit.
pageSize integer ≥ 1 Records per page, clamped to maxLimit. On its own it implies page: 1.
limit integer ≥ 1 Caps an unpaginated read. Also clamped to maxLimit.

Every key is optional. An empty body — or no body at all — is a plain list request, still capped at maxLimit. An unrecognised key is a 400, deliberately: a {"filters": …} typo quietly ignored is a request to return the entire collection.

Conditions

A condition is one of three shapes.

{
  "filter": {
    "category": "65af…",                  // scalar  → equality
    "tag":      ["sale", "clearance"],    // list    → in
    "price":    { "gte": 50, "lte": 250 } // object  → operators
  }
}
Operator Takes Matches
eqa valueEqual to it.
nea valueNot equal to it.
gt · gtea valueGreater than, or greater than or equal.
lt · ltea valueLess than, or less than or equal.
ina list, 1–100 valuesAny of them.
nina list, 1–100 valuesNone of them.

Values are strings, numbers, booleans or null. Mongoose casts them against your schema on the way in, so "gte": "50" on a Number field works exactly as 50 does. Anything else — a nested object, an empty condition, an unknown operator name — is a 400 rather than something to interpret generously.

The same read, both ways

Query string QUERY body
?category=65af… { "filter": { "category": "65af…" } }
?tag=sale&tag=new { "filter": { "tag": ["sale", "new"] } }
?rangeField=price&range=10-100 { "filter": { "price": { "gte": 10, "lte": 100 } } }
?compareField=price&compareOperator=gt&compareValue=50 { "filter": { "price": { "gt": 50 } } }
?s=chair { "search": "chair" }
?sort=-price { "sort": "-price" }
— not expressible { "sort": ["-price", "name"] }
?page=2&pageSize=20 { "page": 2, "pageSize": 20 }

One body can also do what no query string can: two bounds and an exclusion on different fields, a hundred ids, and a multi-key sort, all in one request that no proxy will truncate.

Calling it

const res = await fetch('/api/products', {
  method: 'QUERY',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    filter: { price: { gte: 50, lte: 250 } },
    sort: '-price',
    pageSize: 20,
  }),
});

const { data, pagination } = await res.json();

Browsers and Node's fetch both send QUERY as written — it is a valid method token, not a special case.

curl -X QUERY http://localhost:3000/api/products \
  -H 'Content-Type: application/json' \
  -d '{"filter":{"price":{"gte":50}},"sort":"-price","pageSize":20}'

Handy while developing: -X QUERY with -d is all it takes.

const { data } = await axios.request({
  url: '/api/products',
  method: 'QUERY',
  data: { filter: { tag: ['sale', 'new'] }, sort: ['-price', 'name'] },
});

Axios forwards any method string, but it only serialises data for methods it considers body-bearing — pass the object as data and set the Content-Type explicitly if your version leaves it off.

Asking whether it's there

A client does not have to guess. OPTIONS on the collection lists the methods, and RFC 10008's Accept-Query names the format the body must be in — this library sends it on OPTIONS and on every 415:

OPTIONS /api/products HTTP/1.1

HTTP/1.1 200 OK
Allow: GET, HEAD, POST, QUERY
Accept-Query: application/json

If QUERY is missing from Allow, either the route was turned off, the runtime is too old, or something between the client and the app stripped it.

What gets refused

Request Status Why
{ "filter": { "secretToken": "x" } } 400 Not in filterableFields. Same rule as ?rangeField=.
{ "filter": { "$where": "…" } } 400 A $-prefixed or dotted key is never a field name.
{ "filter": { "price": { "$gte": 1 } } } 400 Operators are spelled gte, not $gte.
{ "sort": "createdBy" } 400 Not in sortableFields.
{ "filters": { … } } 400 Unknown key. Ignoring it would mean returning everything.
{ "page": "2" } 400 JSON has numbers; page, pageSize and limit must be positive integers.
Body sent as text/plain 415 A QUERY body must be JSON.
JSON body, no parser mounted 415 Nothing parsed it. Mount express.json() — the alternative would be silently ignoring the filter.
QUERY /api/products/65af… 404 QUERY is a collection method. Read one record with GET /:id.

Before you rely on it

Node 22.2 or newer. An older runtime rejects QUERY inside its HTTP parser, before Express ever sees the request, and its Express router has no matching verb. The route is then skipped with a single warning rather than breaking the router — the rest of your API is unaffected. Check at runtime:

import { isQueryMethodSupported } from 'express-controller-sets';

isQueryMethodSupported();   // → true on Node 22.2+ with Express 5

What's in front of your app matters more than your app. Some proxies, CDNs, WAFs and API gateways pass only the methods they recognise, and a QUERY request may never reach you. Test through your real edge before shipping a client that depends on it, and keep GET as the fallback — both routes serve the same read.

Turning it off. enableQuery: false leaves the route unmounted, on either router factory. Everything else is unchanged.

createRouter({ model: Product, enableQuery: false });

legacyMode does not open this door. Everywhere else that flag restores permissive 2.x behaviour. QUERY has no 2.x behaviour to restore, so its allowlists are enforced unconditionally: a filter or sort naming a field you never declared is a 400, legacy mode or not. Declare filterableFields and sortableFields, or pass enableQuery: false.

Caching. RFC 10008 makes QUERY responses cacheable, but only for a cache that keys on the request content — and most deployed caches key on the URL alone, where every QUERY to a collection looks identical. Don't put a naive shared cache in front of it. When you need cache keys, keep those reads on GET.

Sorting & pagination in depth

Two knobs the client turns, both bounded by you.

Sorting

createRouter({
  model: Product,
  orderBy: '-createdAt',                        // your default: newest first
  sortableFields: ['price', 'name', 'createdAt'],  // what clients may choose
});

// GET /api/products?sort=price     → cheapest first
// GET /api/products?sort=-price    → dearest first  (the '-' means descending)
// GET /api/products?sort=secretKey → 400 Field 'secretKey' is not sortable.

Your own orderBy is never checked against the allowlist — it's your decision, not the client's. Only a client-supplied ?sort= is validated. If you omit sortableFields, it defaults to everything in query plus whatever field orderBy names.

Pagination

GET /api/products?page=2&pageSize=20

Adding ?page= switches the response into paginated form, with a pagination block alongside the data:

{
  "success": true,
  "data": [ /* … */ ],
  "pagination": {
    "currentPage": 2,
    "pageSize": 20,
    "totalPages": 7,
    "totalRecords": 132
  }
}
Situation How many documents come back
No ?page Up to maxLimit — 100 by default. Never the whole collection.
?page=1, no pageSize 50 — the default page size.
?page=1&pageSize=20 20.
?page=1&pageSize=5000 Clamped to maxLimit. A client cannot enlarge its own page.
?page=abc or ?page=-3 Treated as page 1 rather than erroring.

Paging past the point where offsets stop working

?page=4000 does not jump to page 4,000. It asks MongoDB to walk every one of the 199,950 index entries before it, and throw them away. Add the countDocuments that produces the totals, and both halves of an offset page get slower as the collection grows.

Keyset pagination asks a different question — "everything after this record" — which is one index seek whatever the depth, and needs no count:

createRouter({ model: Product, pagination: 'cursor', sortableFields: ['price'] });
# The first page takes no cursor
GET /api/products?pageSize=50

# → { "data": [ … ], "pagination": { "pageSize": 50, "hasMore": true, "nextCursor": "eyJpIjoi…" } }

# Follow nextCursor for the next one, and so on
GET /api/products?pageSize=50&cursor=eyJpIjoi…

The same applies to QUERY — send "cursor" in the body. Both routes run the same retrieval code, so they page identically.

Measured on 200,000 documents

50 per page page 1 page 1,000 page 4,000
pagination: 'offset' 18.7 ms 19.1 ms 47.8 ms
pagination: 'cursor' 3.6 ms 0.6 ms 0.9 ms

Most of the offset cost is the count — at this size countDocuments alone is 18.7 ms, which is why page 1 costs the same as page 1,000. The skip is what adds the rest by page 4,000, and that part keeps growing. The cursor column does not.

Ties are handled for you. _id is appended to your sort automatically, because a keyset page needs a total order — sort by a field that repeats, like status or a date truncated to the day, and without a tiebreaker records sharing a value are silently skipped or repeated at every page boundary. That is the bug most hand-rolled cursor pagination ships with.

A cursor carries an id, not values. It encodes the anchor record's _id and the sort it was issued for; the server re-reads that record to learn where to resume. So a client cannot hand-craft a cursor that range-filters a field you never made filterable, which a cursor containing raw sort values would allow.

Situation What happens
Last page reached hasMore: false and nextCursor: null.
Cursor reused with a different sort 400. Continuing under another order would skip or repeat records.
The anchor record was deleted 400, saying so. Restart the scan.
?page= in cursor mode, ?cursor= in offset mode 400 either way. Quietly serving the other kind of page would corrupt a scan.
Records inserted mid-scan No repeats. An insert before the cursor shifts every offset by one — this is the bug cursors exist to fix.
Totals needed Cursor mode has none by design. Use offset mode, or count separately.

The rest of the cost knobs

Option What it is for
pagination 'offset' | 'cursor' 'offset' Offset paging with totals, or keyset paging — one index seek per page at any depth. See Sorting & pagination.
maxRelationMatches number 1000 Cap on ids a relational search pulls from a referenced collection.
allowDiskUse boolean false Let MongoDB sort on disk. Sorts above 100MB fail without it.
batchSize number driver default Documents per driver round trip on large result sets.
countStrategy 'estimated' reads collection metadata in O(1) (unfiltered pages only); 'none' drops the count entirely for hasMore.
maxTimeMS A server-side ceiling on every query. The only bound on something slow in the database rather than in Node.
maxPage Refuses deep offset pages outright. Unnecessary in cursor mode.
maxRelationMatches Caps the ids a relational search pulls from a referenced collection — that $in grows with the collection, not with the page. Default 1000.
allowDiskUse Lets MongoDB sort on disk. A sort above 100 MB fails outright without it.
batchSize Fewer driver round trips when walking large result sets.
lean Plain objects instead of hydrated documents. Cheaper per record, but skips toJSON transforms.

None of this substitutes for an index. A keyset page is one index seek only if the sort is indexed — { price: 1, _id: 1 } for ?sort=price. Without a matching compound index MongoDB sorts in memory, and no option here saves it.

Upgrading and suddenly seeing only 100 rows? That's maxLimit doing its job — in 2.x an unpaginated GET / returned every document in the collection, which is a memory spike waiting for a big table. Paginate, or raise the cap deliberately with maxLimit: 500.

Filtering in depth

Three ways to narrow a list, each gated by an allowlist.

Every name in query becomes a query-string parameter of the same name.

createRouter({ model: Product, query: ['category', 'isFeatured'] });

// GET /api/products?category=65af…&isFeatured=true
//   → { category: '65af…', isFeatured: 'true' }

// Repeat a parameter to match any of several values:
// GET /api/products?category=65af…&category=65b0…
//   → { category: { $in: ['65af…', '65b0…'] } }

A parameter that isn't in query is ignored entirely — not an error, just no effect. A parameter whose value arrives as an object (which some query-string parsers allow, e.g. ?price[$ne]=0) is rejected with 400, because that shape is how operator injection gets in.

Two parameters working together: which field, and the bounds.

# price between 10 and 100 (inclusive)
GET /api/products?rangeField=price&range=10-100

# 18 and over — omit the upper bound
GET /api/users?rangeField=age&range=18-

# 100 and under — omit the lower bound
GET /api/products?rangeField=price&range=-100

The field must appear in filterableFields (which defaults to query), otherwise the response is 400. The value is split on a single -, so negative bounds are not expressible — use compareField for those.

One operator against one value.

# price > 50
GET /api/products?compareField=price&compareValue=50&compareOperator=gt

# combine freely with equality filters
GET /api/users?status=active&compareField=age&compareValue=30&compareOperator=lte
compareOperator Meaning
gtgreater than
gtegreater than or equal
ltless than
lteless than or equal
nenot equal
eqequal — the default when omitted

Values that look numeric are converted to numbers; everything else stays a string. Same allowlist as ranges: not in filterableFields means 400.

Why filterable fields are allowlisted at all. Suppose your schema has passwordResetToken and your API never returns it. If a client could write ?compareField=passwordResetToken&compareOperator=gt&compareValue=m, the number of results answers "does this token sort after m?" — and a few hundred of those questions reconstruct the token character by character. The data never appears in a response; it leaks through the result count. Allowlisting the field closes it.

Search in depth

One parameter, ?s= (or ?search=), across as many fields as you list — including fields on related models.

createRouter({
  model: Product,
  search: ['name', 'description', 'category.name'],
});

// GET /api/products?s=wireless
//   matches products whose name OR description contains "wireless",
//   OR whose category's name contains "wireless"

How relational search works

A field with a dot is split at the first dot. The part before it must be a field on your schema declared with ref; the rest is the path to search on the referenced model. The library looks up the matching documents there first, then filters your collection by their IDs — no aggregation pipeline required.

category.name searches name on the Category model
author.profile.name searches the nested profile.name on the Author model
notARef.name clause dropped — the field has no ref

What if no relation matches? You get zero results, not "the search term was ignored". Silently dropping an unmatched search term is how a customer's search for a product nobody sells returns your entire catalogue.

Search terms are treated as text, not patterns

Regex metacharacters in the term are escaped, so ?s=c++ searches for the literal string c++. Terms longer than maxSearchLength (128 characters) are rejected with 400.

Why escaping is not optional. An unescaped search term is a program the client wrote and your database runs. ?s=(a+)+$ triggers catastrophic backtracking inside mongod — one GET request, one pegged database. If you genuinely need clients to pass patterns, allowRawRegex: true exists — put it behind authentication and never on a public endpoint.

The single-field shorthand

createRouter({ model: Post, search: 'title' });
// Still read from ?s= / ?search= — a string just means "one field".
Errors & status codes in depth

Every failure comes back in the same shape. Mount the handler once and stop writing try/catch in route files.

import { errorHandler } from 'express-controller-sets';

app.use('/api/products', productRouter);
app.use('/api/users', userRouter);

app.use(errorHandler);   // AFTER all routes — Express requires this order

The error response

{
  "success": false,
  "error": "Validation Error: price is required",
  "requestId": "0f2a5b8c-…"
}

requestId is echoed into your server log alongside the full message and stack. When a user reports "it said Internal Server Error", that ID takes you straight to the line. A stack field is added only when NODE_ENV=development.

What each status code means

Code When you'll see it Who should fix it
200 Successful read, update or delete. —
201 Record created. —
400 Malformed ID, a field that isn't filterable or sortable, an invalid filter value, a search term over 128 characters, a body with no writable fields, a schema validation failure, a rejected file type, a Multer limit, or an unknown key, operator or non-integer page in a QUERY body. The caller
404 No record with that ID — on read, update or delete. The caller
415 A QUERY body that isn't JSON, or one no mounted body parser handled. The caller, or you — the message says which
409 A unique index rejected the write. The message names the conflicting fields. The caller
500 Anything unclassified. The client gets "Internal Server Error" and a requestId; the details stay in your log. You
503 An upload route was called but S3 environment variables are missing. You

Why 5xx responses are deliberately vague. Mongoose and the AWS SDK write connection strings, internal hostnames, bucket names and index definitions into err.message. Echoing that to the client hands an attacker a map of your infrastructure. Deliberate 4xx messages — the ones this library authors — are returned in full, because they were written to be read by a caller.

Duplicate keys are a 409, not a 500

{ "success": false, "error": "Duplicate value for: email.", "requestId": "…" }

A unique-constraint collision is something the caller can fix by sending a different value, so it is reported as a conflict rather than a server fault. Your front end can show "that email is already registered" without parsing message text.
