Turn it on

Refresh tokens are off by default because they need a field on your user model. Two steps.

  1. Add the session list to your user schema

    refreshTokens: {
  type: [{
    id: String, hash: String, previousHash: String, rotatedAt: Date,
    createdAt: Date, lastUsedAt: Date, expiresAt: Date, userAgent: String,
  }],
  select: false,
},

    Forget it and the app refuses to start, with a message showing exactly this — rather than failing every refresh at runtime.

  2. Enable it — in code or in .env

    AUTH_REFRESH_ENABLED=true
AUTH_REFRESH_ROTATE=true        # true | false
AUTH_REFRESH_EXPIRES_IN=30d
    createAuthRouter({
  model: User,
  token: { secret: process.env.JWT_SECRET, expiresIn: '15m' },
  refresh: {
    enabled: true,
    rotate: true,
    expiresIn: '30d',
  },
});

    Options in code win over the environment, so .env is the per-deployment default. A value that isn't a boolean — AUTH_REFRESH_ROTATE=maybe — stops startup instead of being guessed at. The library reads process.env but never loads .env itself; use dotenv or node --env-file.

What changes

Sign-in responses — register, login, social — gain two fields, and three endpoints are mounted:

MethodPathBodyWhat it does
POST/token/refresh { refreshToken } A new access token and the user's current role. With rotation, also a new refresh token.
POST/logout { refreshToken } Ends that one session. Needs no access token, so it works after expiry.
POST/logout/all — Ends every session of the signed-in user. Needs the access token.

Rotation: on or off

AUTH_REFRESH_ROTATE=true · default

Every refresh issues a new token

The old one stops working. If it is ever presented again, someone is replaying it — so that session ends, and by default every other session of that user too.

Choose this for browsers and anything else where a token might leak.

AUTH_REFRESH_ROTATE=false

The same token until it expires

Simpler for clients that cannot reliably store a new token after each refresh. The session is still revocable through logout, password change and reset.

Choose this for trusted server-to-server clients or constrained devices.

Two tabs refreshing at once is not an attack. A token rotated away within the last graceSeconds (10 by default) is still accepted, so a client racing itself is not signed out for it.

Short tokens, long sessions

An access token that lives for days is a stolen credential that lives for days. A refresh token lets the access token stay short — fifteen minutes — while the user stays signed in for weeks. The refresh token is stored server-side, so it can be revoked; the access token is checked by signature alone, so it is fast.

The client side

Keep both tokens; on a 401, refresh once and retry. Store the refresh token you get back every time — it changes when rotating. Share one in-flight refresh between concurrent requests.

let access = null;
let refreshing = null;

async function refresh() {
  refreshing ??= fetch('/api/auth/token/refresh', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ refreshToken: localStorage.getItem('refreshToken') }),
  })
    .then(async (res) => {
      if (!res.ok) throw new Error('signed out');
      const { data } = await res.json();
      access = data.token;
      localStorage.setItem('refreshToken', data.refreshToken);   // new one when rotating
    })
    .finally(() => { refreshing = null; });
  return refreshing;
}

export async function api(path, init = {}) {
  const send = () => fetch(path, { ...init, headers: { ...init.headers, Authorization: `Bearer ${access}` } });
  let res = await send();
  if (res.status === 401) {
    await refresh();          // throws → send the user to sign-in
    res = await send();
  }
  return res;
}

In a browser, an httpOnly cookie set by your own endpoint is safer than localStorage for the refresh token; mobile apps should use the Keychain or Keystore.

What it does on your behalf
  • Tokens are opaque random values, not JWTs — only an HMAC of each is stored, so a leaked database holds no usable token.
  • Password change and password reset revoke every refresh token. A stolen one does not outlive the password it was issued under.
  • Sessions are capped at maxSessions (5) per user; the oldest is dropped, and expired ones are cleared on each sign-in.
  • Every failure is the same 401 — unknown, expired, tampered or reused are not told apart.
  • A refresh re-reads the user, so a role change or a disabled account takes effect at the next refresh, not when the old token would have expired.
