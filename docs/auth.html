Guides Auth setup

Auth setup

Sign-up, login, roles, refresh tokens and social sign-in on your own user model.

Setup#

createAuthRouter adds sign-up, login, password reset, roles and user management to your user model. It defines no schema.

import { createAuthRouter } from 'express-controller-sets';
import User from './models/User.js';

const auth = createAuthRouter({
  model: User,
  token: { secret: process.env.JWT_SECRET, expiresIn: '15m' },   // secret: 32+ characters
  identifiers: ['email'],                                        // or ['email', 'phone']
  roles: { list: ['user', 'admin'], default: 'user' },
  registerFields: ['name'],
  updateFields: ['name'],
});

app.use('/api/auth', auth);
POST /api/auth/register   { "email": "ada@example.com", "password": "…", "name": "Ada" }
POST /api/auth/login      { "identifier": "ada@example.com", "password": "…" }
→ { "success": true, "data": { "token": "eyJ…", "expiresIn": 900, "user": { … } } }

What your model needs#

Every name below is configurable through fields; these are the defaults. Mark the secrets select: false — the library selects them explicitly where it needs them, and never returns them.

const userSchema = new mongoose.Schema({
  email: { type: String, unique: true, sparse: true },
  phone: { type: String, unique: true, sparse: true },
  password: { type: String, select: false },
  role: { type: String, default: 'user' },

  googleId: String, appleId: String, facebookId: String, githubId: String,

  otpHash:      { type: String, select: false },
  otpPurpose:   { type: String, select: false },
  otpExpiresAt: { type: Date,   select: false },
  otpAttempts:  { type: Number, default: 0, select: false },

  failedLoginAttempts: { type: Number, default: 0, select: false },
  lockedUntil:         { type: Date,   select: false },
  passwordChangedAt:   Date,

  // Only with refresh tokens enabled — see Refresh tokens.
  refreshTokens: {
    type: [{ id: String, hash: String, previousHash: String, rotatedAt: Date,
             createdAt: Date, lastUsedAt: Date, expiresAt: Date, userAgent: String }],
    select: false,
  },
}, { timestamps: true });

Protect your routes#

The auth router carries its own guards. Use them on any router or route:

createRouter({ model: Note, middlewares: [auth.requireAuth], allowedFields: ['title', 'body'] });
createRouter({ model: Report, middlewares: [auth.requireAuth, auth.requireRole('admin')], allowedFields: [] });

app.get('/api/dashboard', auth.requireAuth, (req, res) => {
  res.json({ success: true, data: { userId: req.auth.userId, role: req.auth.role } });
});

Clients send Authorization: Bearer <token>. After requireAuth, req.auth holds { userId, role, claims }.

Refresh tokens#

Keep access tokens short and sessions long. Add the refreshTokens field from the schema above, then turn it on — in code or .env:

AUTH_REFRESH_ENABLED=true
AUTH_REFRESH_ROTATE=true        # true: new refresh token on every refresh · false: reuse it
AUTH_REFRESH_EXPIRES_IN=30d
createAuthRouter({ /* … */ refresh: { enabled: true, rotate: true, expiresIn: '30d' } });
POST /api/auth/login           → { "token": "…", "refreshToken": "…", "refreshExpiresIn": 2592000, … }
POST /api/auth/token/refresh   { "refreshToken": "…" }   → new token (and new refreshToken when rotating)
POST /api/auth/logout          { "refreshToken": "…" }   → ends this session
POST /api/auth/logout/all      Authorization: Bearer …   → ends every session

With rotation on, replaying an old refresh token ends the user's sessions. Changing or resetting a password revokes every refresh token.

Social sign-in#

createAuthRouter({
  // …
  social: {
    google:   { clientId: process.env.GOOGLE_CLIENT_ID },
    apple:    { clientId: process.env.APPLE_CLIENT_ID },
    facebook: { appId: process.env.FB_APP_ID, appSecret: process.env.FB_APP_SECRET },
    github:   { clientId: process.env.GH_ID, clientSecret: process.env.GH_SECRET },
  },
});
POST /api/auth/social/google   { "idToken": "…" }   → same response as login

Tokens are verified with the provider, never trusted as sent. Add googleId etc. to your schema.

More detail#

Customising routes, identifiers and security behaviour.

Recipe: complete auth with welcome email

Email and password, short access tokens with rotating refresh tokens, password reset by email, and a welcome mail. Add the fields from What your model needs to your user schema.

import nodemailer from 'nodemailer';
import { createAuthRouter } from 'express-controller-sets';

const transporter = nodemailer.createTransport(process.env.SMTP_URL);

export const auth = createAuthRouter({
  model: User,
  identifiers: ['email'],
  token: { secret: process.env.JWT_SECRET, expiresIn: '15m' },
  refresh: { enabled: true, rotate: true, expiresIn: '30d' },
  roles: { list: ['user', 'admin'], default: 'user' },
  registerFields: ['name'],
  updateFields: ['name'],

  appName: 'Acme',
  mail: { transporter, from: 'Acme <no-reply@acme.com>' },

  onRegister: async (user) => {
    await transporter.sendMail({
      from: 'Acme <no-reply@acme.com>', to: user.email,
      subject: 'Welcome to Acme', text: `Hi ${user.name ?? 'there'}, thanks for signing up.`,
    });
  },
});

app.use('/api/auth', auth);

Recipe: rate-limit sign-in

Accounts lock after repeated failures, but that doesn't stop someone trying one password against many accounts. Put a limiter on the routes that get guessed at — it runs before the database is touched.

import rateLimit from 'express-rate-limit';

const tight = rateLimit({ windowMs: 15 * 60 * 1000, limit: 20 });

createAuthRouter({
  // …
  middlewares: { login: [tight], register: [tight], forgotPassword: [tight], resetPassword: [tight] },
});
Rename or remove routes

routes renames an endpoint or leaves it out, and middlewares behaves as it does on createRouter — with one addition: an object targets a single route by name.

const auth = createAuthRouter({
  model: User,
  token: { secret: process.env.JWT_SECRET },

  routes: {
    register: '/signup',        // rename it
    login: '/signin',
    social: false,              // never mount it
    modifyRoles: false,
  },

  middlewares: {
    all: [cors()],              // every auth route
    login: [rateLimiter],       // only the ones that get guessed at
    forgotPassword: [rateLimiter],
  },
});

app.use('/api/v1/auth', auth);

Route middleware runs before the guard, so a limiter sheds load without a database round trip first. An unknown route name throws when the router is built rather than doing nothing at request time — and in TypeScript it will not compile.

auth.urls;    // what this instance mounted
// [ { name: 'register', method: 'POST', path: '/signup', access: 'public' },
//   { name: 'login',    method: 'POST', path: '/signin', access: 'public' }, … ]

AUTH_ROUTES;  // everything the factory knows how to mount

Both come from the same table the router is built from, so neither can drift from what is actually served. Every row carries an access level, which is what stops an endpoint being added without a decision about who may call it.

Sign in with email or phone

One field, several identifiers. Each is normalized on the way in, so a phone number reaches the same account however it was typed:

POST /auth/login  { "identifier": "Ada@Example.com",  "password": "…" }
POST /auth/login  { "identifier": "+1 (555) 010-1234", "password": "…" }   # same account as
POST /auth/login  { "identifier": "+15550101234",      "password": "…" }

Email is lowercased, a phone loses its formatting, anything else is trimmed. Supply your own with identifier('nationalId', (v) => v.toUpperCase()).

Rotation on or off
AUTH_REFRESH_ROTATE=true · default

Every refresh issues a new token

The old one stops working. If it is ever presented again, someone is replaying it — so that session ends, and by default every other session of that user too.

Choose this for browsers and anything else where a token might leak.

AUTH_REFRESH_ROTATE=false

The same token until it expires

Simpler for clients that cannot reliably store a new token after each refresh. The session is still revocable through logout, password change and reset.

Choose this for trusted server-to-server clients or constrained devices.

Two tabs refreshing at once is not an attack. A token rotated away within the last graceSeconds (10 by default) is still accepted, so a client racing itself is not signed out for it.

Refresh tokens: client code

Keep both tokens; on a 401, refresh once and retry. Store the refresh token you get back every time — it changes when rotating. Share one in-flight refresh between concurrent requests.

let access = null;
let refreshing = null;

async function refresh() {
  refreshing ??= fetch('/api/auth/token/refresh', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ refreshToken: localStorage.getItem('refreshToken') }),
  })
    .then(async (res) => {
      if (!res.ok) throw new Error('signed out');
      const { data } = await res.json();
      access = data.token;
      localStorage.setItem('refreshToken', data.refreshToken);   // new one when rotating
    })
    .finally(() => { refreshing = null; });
  return refreshing;
}

export async function api(path, init = {}) {
  const send = () => fetch(path, { ...init, headers: { ...init.headers, Authorization: `Bearer ${access}` } });
  let res = await send();
  if (res.status === 401) {
    await refresh();          // throws → send the user to sign-in
    res = await send();
  }
  return res;
}

In a browser, an httpOnly cookie set by your own endpoint is safer than localStorage for the refresh token; mobile apps should use the Keychain or Keystore.

Refresh tokens: security
  • Tokens are opaque random values, not JWTs — only an HMAC of each is stored, so a leaked database holds no usable token.
  • Password change and password reset revoke every refresh token. A stolen one does not outlive the password it was issued under.
  • Sessions are capped at maxSessions (5) per user; the oldest is dropped, and expired ones are cleared on each sign-in.
  • Every failure is the same 401 — unknown, expired, tampered or reused are not told apart.
  • A refresh re-reads the user, so a role change or a disabled account takes effect at the next refresh, not when the old token would have expired.

Social providers in detail

Each provider is verified with the provider. A profile the client sends is a claim about who someone is, and none of these take one on trust.

Provider Send How it is checked
Google { idToken } RS256 signature against Google's published keys, then issuer and audience.
Apple { idToken, name? } The same, against Apple's keys. Apple sends a name only on first authorization, so the client forwards it.
Facebook { accessToken } debug_token confirms the token was minted for your app, then the profile is read.
GitHub { accessToken } or { code } A code is exchanged server-side, so the client never holds the secret. The verified primary email is fetched separately.

A provider only exists once you have configured it — an unconfigured one is a 404, not an open door. Sign-in matches on the provider's account id first, and falls back to a verified email so a social login links to the account that already registered by password.

Any other provider. A provider is one function. Supply verify and it replaces the built-in entirely:

social: {
  discord: {
    idField: 'discordId',
    verify: async ({ accessToken }) => {
      const profile = await fetchDiscordUser(accessToken);
      return { id: profile.id, email: profile.verified ? profile.email : null };
    },
  },
}
What it refuses to do
Attempt Result
Registering with "role": "admin" The role is stripped. Roles have their own endpoint, behind admin.
PATCH /users/:id with a new password or role Both ignored. Each has its own endpoint and its own authorization.
Updating someone else's record 403, unless you administer.
Telling a wrong password from an unknown account Same message, and a decoy hash is verified so the timing matches too.
Guessing a password Counted on the record; the account locks. It survives a restart and holds across every instance.
{ "password": { "$ne": null } } 400. An object where a credential belongs is an injection, not a login.
An admin removing their own admin role 400. It would lock everyone out of the endpoint that undoes it.
Using a token issued before a password change 401. Changing a password ends the sessions that predate it.

token.secret is the whole system. It signs every session and keys every one-time code. At least 32 characters, never in the repository, and rotating it signs everyone out — which is exactly what you want the day it leaks. Generate one with node -e "console.log(require('crypto').randomBytes(32).toString('hex'))".

What this does not do. No rate limiting on the endpoints themselves beyond the per-account lockout — put a limiter in front of /login, /register and /password/forgot (recipe). No email verification flow. Refresh tokens are opt-in — turn them on and keep expiresIn short.
